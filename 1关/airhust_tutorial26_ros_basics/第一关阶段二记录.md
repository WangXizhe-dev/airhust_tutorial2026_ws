# 第一关阶段二 · 让目标点真正发出去

阶段一能在 `rosnode list` 里看到 `/flight_node`。接着读循环，有个很容易忽略的细节：代码一直在给 `setpoint` 赋值，最后交给 `publish` 的却是另一个对象 `fakepoint`。即使把目标高度改成 1.5，后端收到的那条消息也没有这个高度。

## 修改和原因

| 原来的行为 | 改动及理由 |
| --- | --- |
| 主循环按 1 Hz 发布，一秒才发一次 | 改成 20 Hz，正常约每 50 ms 发布一次。后端要求相邻指令的间隔控制在 500 ms 以内，留出的余量可以容纳虚拟机的调度波动。 |
| 给一个对象赋值，再发布另一个对象 | 只保留一份 `geometry_msgs::PoseStamped`，初始目标高度设为 1.5 m。保留 `map` 坐标系，朝向用单位四元数表示。每轮用 `ros::Time::now()` 填写时间戳，再把这份消息发到 `/drone/setpoint`。 |
| 订阅了 `/drone`，而距离传感器在另一个话题上发布 | 订阅 `/drone/sensor/obstacle_distance`，消息类型是 `std_msgs::Float32`。`ros::spinOnce()` 在本轮发布前处理已排队的回调，回调可以更新即将发出的目标高度。 |
| 用距离小于 0 判断降落 | 改为第一次读到距离小于 0.5 m 时，把目标高度改成 0，并记下当时的距离。后面的循环持续发布高度 0，起飞高度只在启动时设置一次。 |

## 在课程虚拟机里验证

在两个 zsh 终端分别进入 `~/airhust_tutorial2026_ws/1关/airhust_tutorial26_ros_basics`。终端一运行：

```zsh
source install/setup.zsh
catkin_make -j2
source devel/setup.zsh
zsh ./run_sim.sh
```

等后端启动，终端二运行：

```zsh
source install/setup.zsh
source devel/setup.zsh
roslaunch drone_bringup mission.launch
```

在 Ubuntu 20.04、ROS Noetic 的一次实跑中，`/drone/state` 的高度达到 **1.50 m**，控制节点在传感器报出 **0.470 m** 时发起降落，后端随后打印了 **“成功降落（高度 0.00 m）”**。观测到的相邻设定点时间戳最大间隔为 **0.137 s**，状态反馈中也观察到了 `setpoint_ok=true`。

有个值得记下的测试细节：这次监听器收到的最后一个高度约为 0.05 m，而后端自己的着陆日志已记录 0.00 m。后端会在判定成功后退出，所以验收时同时核对了状态话题和后端日志。这也是为什么单看 `flight_node ready` 还不够：那行日志只能证明节点已经启动。

第二次从头复测，峰值高度仍为 1.50 m，首次低于阈值的距离约为 0.470 m，最大设定点间隔为 0.180 s。后端再次记录成功降落。把话题样本与后端终态一起核对，综合检查通过。

## 答辩时怎么讲

如果被问到“把目标高度写成 0，飞机就已经落地了吗”，可以沿着三条话题回答：传感器先用距离话题触发回调，控制节点再用设定点话题持续请求下降，最后用状态话题观察实际高度，并看后端的着陆判定。这样能讲清楚**测到了什么、要求飞机做什么、飞机最后做到了什么**。
