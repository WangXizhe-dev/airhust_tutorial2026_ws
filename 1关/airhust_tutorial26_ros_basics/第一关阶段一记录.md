# 第一关阶段一 · 让 `flight_node` 跑起来

第一次跑 `catkin_make`，报错里最有用的是这一点：CMake 已经找到了 `geometry_msgs`，catkin 却说 `package.xml` 没有把它声明为构建依赖。顺着报错对照两个文件，发现 `geometry_msgs` 和 `std_msgs` 都写在了 `CMakeLists.txt` 里，包清单却漏掉了它们。

## 这次改了什么

### 在 `package.xml` 里补齐依赖

给 `geometry_msgs` 和 `std_msgs` 各加一条 `<depend>`。`flight_node.cpp` 用 `geometry_msgs::PoseStamped` 发布目标位姿，用 `std_msgs::Float32` 接收障碍距离，所以这两个消息包都是 `drone_bringup` 的直接依赖。清单采用格式 2，`<depend>` 一条就能声明构建、构建导出和运行三类依赖。

原来 `drone_backend` 已有构建依赖和运行依赖两条声明。把它们合并为 `<depend>drone_backend</depend>`，同时补上构建导出这一层，因为下面的 `CATKIN_DEPENDS` 也会导出它。

### 在 `CMakeLists.txt` 里补齐后端依赖

把 `drone_backend` 加进 `find_package(catkin REQUIRED COMPONENTS ...)` 和 `catkin_package(CATKIN_DEPENDS ...)`。仓库里已有的 `example_listener.cpp` 会包含 `drone_backend/DroneState.h`，然后用这个类型订阅 `/drone/state`。把后端列为 catkin 组件后，现有的 `${catkin_INCLUDE_DIRS}` 就能带上后端的头文件路径。`CATKIN_DEPENDS` 则把这个依赖写进本包导出的构建配置。

这里我记住了一点：**找到包**和**声明依赖**是两件事。`find_package` 成功，只说明 CMake 能在当前环境里找到那个包。catkin 还会检查 `package.xml` 里有没有声明这个依赖。第一次编译正是卡在了这里。

### 给 `flight_node.cpp` 配一个构建目标

对照 `mission.launch` 看，里面要启动的是 `drone_bringup` 包里的 `flight_node`。源码目录里确实有 `flight_node.cpp`，原来的 CMake 配置却只会编译 `example_listener`。因此需要补上这两行：

```cmake
add_executable(flight_node src/flight_node.cpp)
target_link_libraries(flight_node ${catkin_LIBRARIES})
```

第一行用这份 C++ 源码生成名为 `flight_node` 的可执行文件。第二行把它链接到 catkin 提供的库，例如代码调用的 `roscpp`。这样就能对上三个名字：源码 `flight_node.cpp`、构建目标 `flight_node`、launch 里的 `type="flight_node"`。

## 怎么确认修好了

在课程的 Ubuntu 20.04 / ROS Noetic 环境里，从第一关工作空间运行：

```zsh
source /opt/ros/noetic/setup.zsh
source install/setup.zsh
catkin_make -j2
source devel/setup.zsh
roslaunch drone_bringup mission.launch
```

第一份 `setup.zsh` 加载 ROS Noetic，第二份把题目提供的预编译后端加入当前终端的环境。编译完成后加载本工作空间的 `devel/setup.zsh`，这个终端才能优先找到刚构建的 `drone_bringup`。`source` 只影响当前 shell，所以换了终端也要留意当前加载的是哪个工作空间。

实际验证时，编译返回 `0`，launch 日志出现 `flight_node ready`，另用 `rosnode list` 查到了 `/flight_node`。这次验证到节点能启动为止。起飞、障碍距离判断和降落是阶段二，等接上后端再按实时状态验收。

## 答辩时我会怎么说

第一关的目录是一个工作空间，`src/drone_bringup` 是里面的包，`flight_node` 是这个包里编译出来并实际运行的节点。碰到同类问题，我会先看第一条错误，再按顺序核对包清单、CMake 构建目标和 launch 的 `pkg`、`type`。如果编译成功了，换个终端却找不到包，我会先检查有没有 `source` 对应工作空间的环境文件。
